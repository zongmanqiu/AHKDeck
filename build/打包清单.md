# 发行包清单（打包规矩）

本文件是 AHKDeck 发布压缩包的**唯一白名单**。以后每次打包都按这里执行，新增文件先进此表再进包。

## 谁打包、用什么

- 打包由助手（agent）执行，用户不需要手动操作。
- 压缩工具固定为 **7z**，输出 **zip**（`7z a -tzip -mx=9`）。
- 执行入口：`.main\build\6_package.ps1`（自动找 7z、按白名单暂存、生成 zip 并列出条目）。
- 暂存目录：`.temp\package-<版本>\`；成品：`.build\AHKDeck_<版本>.zip`。
- 版本号只有一处来源：`.main\CMakeLists.txt` 的 `project(AHKDeck VERSION ...)`。

```powershell
powershell -ExecutionPolicy Bypass -File .main\build\6_package.ps1
```

## 必须入包

| 包内路径 | 来源 | 说明 |
|---|---|---|
| `AHKDeck.exe` | `.build\` | 主程序（静态 CRT，无需 VC++ 运行库） |
| `AutoHotkey64.dll` | `.build\` | 定制 AutoHotkey_H 内核，必须与 exe 同目录 |
| `Scripts\` | 打包脚本创建（空目录） | 用户脚本目录；**不复制** `.build\Scripts`，否则开发机上正在试的脚本会跟着发出去（m123 起不再随包任何脚本或菜单桥） |
| `docs\` | `.build\docs\`（构建期由 `.main\docs\` 与官方清单落盘） | `MCP接入.md`（帮助 > MCP 接入 打开的就是这份）；`scripts.json` 是随包脚本清单，下载器打开时先读它 |
| `licenses\` | `.main\licenses\` | 上游许可原件：GPL-2.0、LGPL-2.0-with-FLTK-exception、说明 |
| `LICENSE` | `.main\LICENSE` | 本程序许可 |
| `THIRD-PARTY-NOTICES.md` | `.main\THIRD-PARTY-NOTICES.md` | 第三方组件与分发义务 |

`docs\`、`licenses\`、`LICENSE`、`THIRD-PARTY-NOTICES.md` 由构建的 POST_BUILD 阶段落到 `.build\`，打包只从 `.build\` 取，保证包内与构建产物一致。

## 禁止入包

这些是运行期生成的本机状态或构建残留，**任何情况下都不进 zip**：

| 项目 | 原因 |
|---|---|
| `settings.json` | 用户本机配置（几何、占比、更新源等），首次运行自行生成 |
| `hotkeys.txt` | 用户本机快捷键覆盖项 |
| `Logs\` | 会话日志 |
| `Backups\` | 升级前备份 |
| `update.cache.json` | 上次更新检查缓存 |
| `*.dmp`、崩溃 `*.txt` | 崩溃转储 |
| `.temp\` | 下载缓存与构建中间物 |
| `ahkdeck_backup\`、`ahkdeck_update.bat`、`ahkdeck_update.log` | 升级过程的临时文件 |
| 任何 `*.zip`、`*.obj`、`*.pdb`、`*.lib` | 打包/编译产物 |

`update.json` 是**远端更新清单**，发布在仓库 `main`，不随包。

## 打包前检查

1. `.main\build\4_build.bat` 成功，`.build\AHKDeck.exe` 与 `.build\AutoHotkey64.dll` 同批生成。
2. `.main\build\5_test.bat` 全绿。
3. `.build\AHKDeck.exe --version` 输出的版本与 `CMakeLists.txt` 一致。
4. `.build\Scripts\` 存在（`deck_scripts` 目标只负责创建该目录）；包内 `Scripts\` 是**空目录**，由打包脚本现建，不复制开发机上的脚本。

## 打包后验证

1. zip 条目只出现在上面的白名单里，且白名单各项都在。
2. 解压到空目录后 `AHKDeck.exe --version` 正常、`docs\` 与 `licenses\` 可打开。
3. 记录 zip 路径、字节数与条目数，写进对应计划文档。

## 发布顺序

1. 生成 zip 并核对清单。
2. 上传 Gitee Release（`0.2.0` 这类不带 `v` 的标签），标题与发布说明取 [HISTORY.md](../HISTORY.md) 对应小节；再上传 GitHub Release。
3. 把 `update.json` 的版本、日期、说明与两个下载地址对齐到已上传的资产。
4. 只要 `update.json` 已被推送，就必须确认两个下载地址返回 200——指向不存在的资产会让老版本用户的更新下载 404。若清单先于资产提交，上传后立刻用 HEAD 请求复核。
