# 开发指南

面向维护者：脚本怎么组织、头部怎么写、注释怎么落、版本怎么升、怎么测、怎么出货、
要登记哪些信息、登记在哪。使用者看 [`README.md`](https://gitee.com/qiuzongman/ahk-v2-scripts/blob/master/README.md) 就够；每个脚本自己的说明
与历史在它的 `info/` 里。

> **本文件只管「脚本作为仓库成员」的事**：文件结构、头部元数据、登记项、版本、测试、发版。
> GUI 的视觉规范（配色令牌、控件配方、踩坑表、自检清单）与像素取证手法属实现层知识，
> **不在本文件**——范本源码是它们的载体，写 GUI 前先读形态最像的那一份（§8 第 2 步）。
> 脚本源码注释里出现的「§10.x」「§6.1」沿用旧编号，指向随宿主发行的 UI 规范文档，编号未变。

> 本仓库的布局借鉴了同作者的 CurSeen-Scripts（每脚本一个稳定文件夹 + `info/` 文档 +
> 根目录开发指南），但**按 AHK 的现实裁过**：宿主直接扫 `.ahk` 平铺运行；单文件发 `.ahk`，
> 多文件走标准 zip（§9）；机器清单 `scripts.json` 与每脚本一份 `history/<id>.json` 供宿主下载
> 并显示版本历史（§7.1）。差异见 [§1.1](#11-与-curseen-scripts-的差异)。

## 1. 目录约定

```text
ahk-v2-scripts/
├─ README.md              使用者入口：脚本列表 + 怎么用 + 导航
├─ 开发指南.md            本文件（维护者）
├─ LICENSE                AGPL-3.0 全文（全仓唯一一份）
├─ .gitignore             忽略运行时产物（ini / 备份）；仓库根 history/ 不忽略
├─ .gitattributes         文本归一（eol=lf）
├─ scripts.json           机器清单（生成器产出，宿主下载用，§7.1）
├─ history/               每脚本一份 <id>.json 版本历史清单（m221，§7.1）
├─ tools/
│  ├─ make_index.py       扫脚本头部 → 生成 scripts.json（Python3，§7.1）
│  ├─ publish_version.py  建 release tag / 传附件 / 更新 history（§7.2）
│  └─ pack_script.py      多文件脚本打标准 zip（§9.2）
└─ scripts/               全部官方脚本，一个子目录 = 一个脚本（平铺，不按年/类型分）
   ├─ 打开方式清理/
   │  ├─ 打开方式清理.ahk   脚本本体（文件夹名 = 文件名 = @name）
   │  └─ info/
   │     ├─ README.md      这个脚本的功能/入口/写入位置/风险/不做
   │     └─ HISTORY.md     这个脚本的版本历史（只增不改）
   ├─ 夜灯/
   │  ├─ 夜灯.ahk
   │  └─ info/{README.md, HISTORY.md}
   └─ 双击防抖/
      ├─ 双击防抖.ahk
      └─ info/{README.md, HISTORY.md}
```

- **一个脚本一个文件夹**：`scripts/<名>/<名>.ahk` + `scripts/<名>/info/`。文件夹名、
  文件名、头部 `@name` 三者一致；改名要三处一起改（外加同名 ini、窗口/托盘标题，见 §5）。
- **不按年、不按类型分顶层目录**：旧版的 `2026/` 已废。脚本会跨年维护，按年归档会让
  "同一个脚本散在多个年份目录"，出货与改名都难对上。
- `info/` 是**两件式**：`README.md`（人读说明）+ `HISTORY.md`（版本历史）。许可证全仓共用
  根目录一份 `LICENSE`，**不在每个脚本里再放一份**。
- **运行时产物一律进「同名文件夹」（硬准则，2026-11-15 立）**：脚本要落盘的任何东西——
  配置 ini、备份、历史、扫描报告、自测输出——路径都必须是 `A_ScriptDir "\<脚本名>\"` 下的文件，
  也就是与脚本**同名**的那个子文件夹。

  ```text
  .build\Scripts\            出货目录是平铺的
      夜灯.ahk
      夜灯\                  ← 与脚本同名
          夜灯.ini           ← 设置
          selftest-result.txt ← --selftest 默认输出
          history\           ← 备份/历史
  ```

  为什么不允许「脚本旁直接放一个 ini」：`.build\Scripts\` 是平铺的，六七个脚本的 `xxx.ini`、
  `selftest-result.txt` 全混在一起，用户分不清哪个文件属于哪个脚本，换版本/删脚本时也不知道
  该删哪个。一个脚本 = 一个文件夹，产物归位，卸载就是删那个文件夹。

  四条配套要求，缺一不算做到：
  1. **目录按需创建**：`if !DirExist(gDir) { try DirCreate(gDir) }`，只在真要写之前建；
     纯读场景不要凭空多出一个空文件夹。
  2. **默认输出也走这条**：`--selftest` / `--report` / `--dump` 不带参数时的默认路径同样是
     `A_ScriptDir "\<脚本名>\..."`，不许落在脚本旁。用户显式传了路径才按用户给的。
  3. **旧位置做一次性迁移**：新位置没有、旧位置有时整份复制过去，**旧文件保留不动**
     （用户回退版本时设置还在）。样板见 `双击防抖` 的 `MigrateConfig()`。
  4. **`.gitignore` 要盖住**：新增一种产物名就同步加规则，产物不进仓库。

  不写宿主目录、不写仓库根。测试临时文件写 `%TEMP%` 可以，但那只能由测试参数显式传入，
  不能当默认值。
- 仓库**只放手写源码与文档**：不放编译产物、不放第三方库源码、不放打包 zip。

### 1.1 与 CurSeen-Scripts 的差异

借鉴的是"每脚本稳定文件夹 + `info/` 文档 + 根开发指南 + HISTORY 只增不改"这套形状。
按 AHK 现实裁掉/改动的有六处，写新脚本前先知道：

| CurSeen-Scripts | 本仓库 | 为什么 |
|---|---|---|
| `pack.json` + `scripts.json` 机器清单 | 只有 `scripts.json` + `history/<id>.json` | 宿主已消费清单做官方下载；历史清单让宿主显示「版本历史」链接（§7.1） |
| 发布 zip + 在线安装/升级/卸载 | 单文件发 `.ahk`，多文件发标准 zip；都进 release，宿主可下载安装，不做自动升级 | 版本权威在 release tag，不在本地（§7.2） |
| `info/` 三件式（含每包 `LICENSE`） | **两件式**（README + HISTORY） | 全仓共用根目录一份 AGPL-3.0，不逐脚本复制 |
| `scripts/*.lua` 子目录放脚本 | 单个 `.ahk` 直接放在 `scripts/<名>/` | 一个脚本一个文件，无需再套一层 |
| `tools/` 官方工具源码 | 索引 / 打包 / 发版工具（Python3） | 脚本纯 AHK v2、不携带外部 exe/模型；工具只在维护时用 |
| 头部无统一元数据块 | 保留油猴式 `==UserScript==` 块（§2） | 这是本仓库已有的头部规矩，沿用 |

来源也不同：CurSeen 的鼠标特效包是上游项目的独立重实现；本仓库的"复刻/移植"指向
**作者自有项目**（OpenWithCleaner、KissLight），不是外部第三方，出处写在各脚本头部注释与 `info/README.md`。

## 2. 头部块（油猴式元数据）

每个脚本**文件最前**必须是如下注释块（形状照搬 Tampermonkey 的 `==UserScript==`，
注释符用 AHK 的 `;`）。**下面 12 个字段全部必填、非空**（官方脚本硬规矩，生成器逐项校验，
缺一个就报错）；可在此之上增加字段，不可缺省：

```ahk
; ==UserScript==
; @name         脚本名
; @id           english-script-id
; @namespace    https://gitee.com/qiuzongman/ahk-v2-scripts
; @version      1.0.0
; @description  一句话说明
; @author       邱宗满
; @date         2026-11-11
; @license      AGPL-3.0
; @homepageURL  https://gitee.com/qiuzongman/ahk-v2-scripts
; @requires     AutoHotkey v2.0
; @host         AHKDeck 0.2.2+（亦可独立运行）
; @entry        托盘菜单「…」
; ==/UserScript==
```

| 字段 | 含义 | 与油猴对照 |
|---|---|---|
| `@name` | 脚本显示名（= 文件夹名 = 文件名） | 采用 |
| `@id` | 永久英文身份（`[a-z][a-z0-9-]*`，发布后不许改，release tag 的一部分，§5） | 扩展（油猴无此字段） |
| `@namespace` | 命名空间（仓库 URL） | 采用 |
| `@version` | 语义化版本（§5） | 采用 |
| `@description` | 一句话简介 | 采用 |
| `@author` | 作者 | 采用 |
| `@license` | SPDX 许可证名（全文见根 `LICENSE`） | 采用 |
| `@homepageURL` | 项目主页 | 采用 |
| `@date` | 最近一次修订日期（YYYY-MM-DD） | 扩展（油猴无此字段） |
| `@requires` | 运行环境要求 | 扩展 |
| `@host` | 宿主及版本下限／可独立运行 | 扩展 |
| `@entry` | 入口（托盘菜单项／命令行分支） | 扩展 |

**不硬编码全局热键**：官方脚本不自设全局热键（如 `^!+n::`）——全局热键由 AHKDeck 统一
置顶/指派，脚本里写死会和宿主、和别的脚本抢键。`@entry` 只写托盘菜单项或命令行分支，不写热键。
脚本**自有窗口聚焦时**的上下文按键（`#HotIf <自己的 GUI> … Delete::`）是正常列表 UI，不算全局热键，可保留。

**弃用的油猴字段**：`@match` `@include` `@exclude` `@grant` `@require` `@resource`
（浏览器语义，AHK 无对应）、`@updateURL` `@downloadURL`（本仓库不做自动更新）。

块后空一行，再写许可证/来源/偏离等说明注释（§3），然后是 `#Requires` 与代码。

## 3. 注释规矩

- **默认不写注释**。只在"为什么"不显然时写一行：隐藏约束、微妙不变量、针对某个 bug 的
  绕行、会让读者意外的行为。删掉它会让未来读者困惑，才写。
- **不写"代码做了什么"**：命名已经说清楚的事不再复述。不写"用于 X 流程""为 Y 问题加的"
  这类引用当前任务/调用方的话——那些属于提交说明，会随代码演化腐烂。
- 头部块后的说明注释是例外：它承载**许可证、来源、与原项目的偏离、有损行为、无 GUI 分支**
  这些"读代码前就该知道"的事，可以成段，但只写事实，不写营销。
- 界面文案只中文；注释也中文。

## 4. 编写约定

- 纯 AHK v2（`#Requires AutoHotkey v2.0`），x64；**不依赖宿主私有 API**——托盘菜单是唯一入口桥。
- 默认 `#SingleInstance Force`、`#NoTrayIcon`：宿主内由宿主镜像托盘菜单；独立运行时
  （按 `A_AhkPath` 不是宿主判定）显示自己的托盘图标，菜单入口照常可用。
- **纯托盘脚本要自己声明常驻**：内核只把「热键/热字串、`Persistent()`、启用的定时器、
  剪贴板监视、InputHook、可见的 GUI 窗口」当作常驻理由，**往 `A_TrayMenu` 加项不算**。
  入口只有托盘菜单、又拿一个面板当界面的脚本，不写 `Persistent(true)`，面板一关脚本就正常结束
  （夜灯 1.0.1 踩过：去掉自设热键后，面板成了唯一的"活着"凭据）。
- 界面只中文；字体 Microsoft YaHei UI；**GUI 的配色、字号、控件配方不在本文件规定**——
  动手前先照抄一份同类范本源码（§8 第 2 步），令牌与配方以范本为准，不在脚本里自造色值或字号；
  破坏性操作要有确认与失败提示，**不假成功、不静默兜底**。
- **关闭口径按窗口形态分**：以窗口为唯一入口、没有托盘菜单的脚本（文件时间修改、文件哈希、硬件信息），
  点标题栏关闭按钮必须 `ExitApp()`，不能只 `Destroy()` —— 窗口没了进程还在，宿主会话会一直
  显示 running；面板型脚本（夜灯）关面板只 `Destroy()`，靠 `Persistent(true)` 继续待命，
  托盘随时可再打开。有自绘滚动条/拖动定时器的，退出前先 `Stop()` 再退出（K21）。
- 退出清理：`OnExit` 里卸钩子/关句柄/删字体；**不还原用户已生效的显示设置**
  （屏幕当前的样子就是用户最后选的样子）。
- 列表类 UI：能原地更新就不整表重建；重建时保持滚动位置与焦点。
- **不改进程工作目录，路径一律用 `A_ScriptDir` 拼绝对路径**：宿主的 `A_WorkingDir` 是
  **进程级**共享状态，内核补丁只在**加载期**为主脚本补一次脚本目录（为了让相对 `#Include`
  按脚本目录解析），并不是每会话一份目录。脚本运行时调 `SetWorkingDir` 会把整个进程的 cwd
  翻到自己的目录，影响其他脚本与宿主；宿主已把日志根固定成 exe 旁的绝对路径来对抗这一点。
  读写脚本旁文件一律 `A_ScriptDir "\<名>.ini"`，不写相对路径。
- 新脚本照抄头部块与上述约定。

### 4.1 新脚本接入自检

新脚本（含外部 AI 产出的脚本）进仓前照 §6「单脚本测试」自己跑一遍：
`--validate` + `--selftest` + `scripts/<名>/test/run.py`。以前有个
`make_index.py --audit` 把全仓硬规矩一次性扫一遍，2026-11-14 已删 —— 理由是改 A 脚本时
它会把 B 脚本的旧账一起翻出来，逼着人去动不该动的文件（AGENTS.md 第 12 条）。
手读一遍指南不能替代实跑。

> **不适用的经验**：街机/模拟器宏脚本里的连发（SetTimer 自引用递归）、
> `#MaxThreadsPerHotkey 1`、`~*` 全局热键防抢占，都建立在「脚本自设全局热键」之上。
> 本仓库 §2 明令不自设全局热键、入口只有托盘菜单，这批经验不适用于官方脚本，不要照搬。

## 5. 版本规矩

语义化版本 `MAJOR.MINOR.PATCH`，从 `1.0.0` 起（首次发布）。三档判定与宿主 AHKDeck 一致（用户裁决，m217），只是本仓库脚本从 `1.0.0` 起步：

| 位 | 判定口诀 | 例子 |
|---|---|---|
| MAJOR | **升级后，用这个脚本的人（或宿主）必须改变已有用法或数据才能继续用？** | 入口改了；配置 / ini 字段格式改了且需迁移；写入位置改了；托盘项重命名且不兼容旧入口 |
| MINOR | **升级后，能做一个以前完全做不到的事？** | 加一个命令行分支、加一个托盘项、支持新的目标类型 |
| PATCH | **功能集合没多没少，只是更对、更顺？** | 修 off-by-one、原地排序提速、UI 微调、文档与注释 |

- **混合取最高**：一次发版同时含多档改动，按最高档升；第二位进位时第三位归零。
- **用户不可见的机制改进一律 PATCH**：内部重构、门禁、打包脚本改动属此类。

- `@date` 每次修订都更新成当天（YYYY-MM-DD），与版本号无关。
- **`@id` 是脚本的永久英文身份**（m221）：小写字母开头，只含小写字母/数字/连字符
  （`[a-z][a-z0-9-]*`），全仓唯一，与脚本名对应。**一旦发布就不许改**——release tag 是
  `<id>-<版本>`，改 id 等于把全部历史版本从索引里抹掉。新脚本由 `new_script.py` 生成时
  必须显式提供（§8 第 2 步），生成器会校验形状与唯一性。
- **改名 / 纯文档不升版本**：仅改显示名、改 README/注释而行为不变，不动 `@version`。
  首次发布前的改名（如「鼠标左键双击最小间隔」→「双击防抖」）算 `1.0.0` 的一部分，不另起版本。
- **改名要同步五处**：文件夹名、文件名、`@name`、同名 ini（`A_ScriptDir "\<名>.ini"`）、
  窗口与托盘标题（`Gui(, "<名>")` / `A_IconTip`）。旧名只允许作为 `info/README.md` 与
  头部注释里的"曾用名"留痕，代码里不许残留。
- **HISTORY 只增不改**：每次发版在该脚本 `info/HISTORY.md` 最上面加一段
  `## <版本>（YYYY-MM-DD）`，写这一版改了什么；旧段一个字不动。

## 6. 测试

- **语法/加载门禁**：宿主 `--validate <脚本>` 返回 `{"ok":true,"rc":0}` 才算过。
  改完每个脚本都跑一遍。
- **自测分支**：有破坏性/注册表操作的脚本应自带 `--selftest [输出路径]` 无 GUI 分支，
  只动自建键、结束即清理，`rc=0` 全绿。自测要能**红**：把被测缺陷还原一次，看它真的失败，
  再还原——一个"对旧代码也绿"的回归测试不是测试。
- **取证分支**：只读扫描类脚本再配一个 `--report [输出路径]`，把每一步的行数/耗时、
  命中数与缓存规模打出来（`打开方式清理` 的做法：15 步逐条 `step<n> <函数名> rows=<新增> ms=<耗时>`，
  末尾 `rows_total=/scan_ms=`）。定位「慢在哪一段」「某一步是不是白跑」时，这比翻代码猜快得多，
  而且是可以贴进 `HISTORY.md` 复述的硬读数。
- **内核分离门禁**：脚本不得引用宿主私有内核符号。用内核名扫**当前这一个**脚本
  （`scripts/<名>/<名>.ahk`），命中即说明脚本越过了"托盘菜单是唯一桥"的边界，要改回去。
  不要去扫全仓 —— 别的脚本命中与本轮无关（AGENTS.md 第 12 条）。
- **实机门禁（硬规矩，作者定）**：官方脚本必须经 **AHKDeck MCP 接入**完成宿主实机闭环，
  才算交付——`list_scripts` → `run_script` → `get_session_output` → `stop_script`；
  （发行包内有 `docs\MCP接入.md` 可查全表）。CLI `--validate` 与独立解释器实跑
  是**前置门禁**，不能替代它：`--validate` 只解析不执行，独立解释器不在宿主运行环境里。
  实机结论（各调用成败、会话输出要点、停止确认）记入 `info/HISTORY.md` 或对应 `.plan` 文档留痕。
- **界面类脚本另加一道几何量测**：脚本常驻并建了窗口时，跑 `inspect_ui`（按会话返回顶层窗口与
  全部子控件的类名、文字、客户区坐标、样式位、DPI），把每项 `client` 与源码里写的 `x,y,w,h`
  逐行比；颜色疑义用 `ui_pixel` 取单点。
- **交互与像素回归（2026-11-16 起 18 工具，同日加判定工具后 20 工具）**：`send_input` 注入
  点击/滚轮/键盘（K32 这类只有真点一下才暴露的 bug 现在能自动验了：点击 → `inspect_ui`
  看状态/`get_session_output` 看回调输出）；改 UI 前后各 `capture_ui`（滚轮/点击后截图带
  `stable=2` 防截到重绘中间态）再 `ui_diff`，把 `diff_pixels` 与 `bbox` 写进测试断言或 HISTORY。
  判定：`assert_ui` 对界面树直接给 `verdict=pass/fail`，异步就绪用 `wait_ui` 先等再断，
  测试脚本可以把 verdict 当硬断言。字段语义与判读口径见发行包内 `docs\MCP界面量测.md`。
  判读口径：与源码 `x,y,w,h` 差 1px 多为父块/内块内缩所致；空 ListView 露出的是
  外框线色，不是缺陷。
- **报错先看 `source`，不要自己数行**：`run_editor` / `get_session_output` 的 `errors[]` 每条都带
  `line`（行号）、`source`（该行原文）、`func`（出错时在哪个函数）、`stack`（调用链，顶层在前，
  每帧 `文件 (行) : [函数] 该帧原文`），`warnings[]` 是 `#Warn` 类。同样是第 8 行，`stack` 里的
  `> Timer` / `> OnMessage` 决定这是定时器还是消息回调进来的两种修法。
  同类实案与更多字段见发行包内 `docs\MCP接入.md`「出错之后」一节。
- **写 AHK API 之前先 `lookup_help`，不要凭记忆**：`lookup_help(query)` 查的是随包的离线索引
  （356 页，与内核同为 2.0.31），给签名、每个参数的类型与含义、返回值。
  写错的 API 多半不是语法错——参数顺序颠倒、选项名拼错、把格式串当初始值（`Gui.Add("DateTime",…,
  第三参数)` 是显示格式串不是初始值）——这类代码能解析也能跑，`validate_editor` 拦不住。
  `exact=false` 只是模糊命中，先看候选；`name` 可能是合页名（`Send / SendText / …`、`Run / RunWait`），
  看 `aliases` 确认是哪一个。更多示例见发行包内 `docs\MCP接入.md`「语法查询」一节。
- **单脚本测试（本仓库唯一形态）**：每个脚本自己的实机测试放在 `scripts/<名>/test/`，
  一条命令跑自己：`python scripts/<名>/test/run.py`。测试里 `from mcp_client import MCP`
  （`tools/mcp_client.py`，起 MCP 临时实例、只关自己拉起的进程），靶窗 `.ahk` 与断言
  同目录放着，靶窗版式改了断言跟着改。
  **只有 `--selftest` 分支的脚本还不算有测试**：那个分支只证算法，不证窗口真的画出来了。
  ```text
  scripts/版式验收/test/
    run.py        # 断言：读数、参考层位置、参考层四边像素、状态条文案
    target.ahk    # 靶窗（故意 +AlwaysOnTop，复现被压住的那个 bug）
    README.md     # 怎么跑
  ```
  新脚本进仓时可以没有 `test/`，但**下次改到它**就得补上；补的时候只碰它自己。
- **清单**：改了脚本头部/版本/名字，跑 `python tools/make_index.py` 重生成 `scripts.json`。
  生成器**只有生成这一个动作**，没有 `--check/--audit/--selftest`：那三个曾经存在，
  因为「改 A 却要全仓绿」而被删掉（2026-11-14，AGENTS.md 第 12 条）。
- **静态检查**：`python tools/ui_static.py <脚本名>` —— 调色板/字号/版本四处一致/
  出货件逐字节一致，**一次只查一个脚本，必须给名字**，没有「跑全部」。
- **码表门禁**：`python tools/check_codes.py <脚本名>` —— 脚本里若有枚举码表
  （SMBIOS 类型码、CIM 枚举、`DISPLAYCONFIG_*`、Rank 位段），逐项比对权威表：
  覆盖是否完整、有没有越界码位、文案对不对得上、关键码位（DDR5=0x22 / DIMM=8 …）是否还成立。
  **码表错一位不报错、不崩、不少画一个控件，只会安静地把 DDR5 显示成 HBM3**——
  2026-11-15 漏掉的三处全是这一类：本机 DDR4(0x1A)、单 Rank(attr=0x01)、台式机(3)
  恰好都落在全表唯一正确的格子上，33 项自测全绿也照不出来。
  加 `--from-dmidecode <dmidecode.c>` 会把工具内置的权威表反向与上游 C 源码逐项核对，
  防止工具自己走样。同样**一次只查一个脚本，必须给名字**。
  > 判断一条码表结论靠不靠得住，看的是**对着规范/上游逐项核过没有**，不是"跑一遍没报错"。
  > 另一个坑：**自测断言本身可能按错误理解写**，那样只会把 bug 固化成 PASS
  > （曾把 `TypeName(32)="DDR5"`（32 其实是 HBM）、`RankName(0)="1R"` 写成断言，两条都绿）。
- **GUI 行为**：像素是唯一发现器。门禁全绿不等于界面正确；涉及布局/交互的改动要实际跑起来
  看像素，别拿"功能存在"当"功能生效"。

## 7. 出货与发版

宿主与本仓库**分离**：本仓库是脚本唯一真源，宿主只负责运行。

1. 改脚本 / 改说明 / 改 LICENSE；在该脚本 `info/HISTORY.md` 最上面加 `## <新版本>` 一段。
2. 按 §5 升 `@version`、更新 `@date`；纯文档/改名不升版本。
3. **重生成清单**：`python tools/make_index.py`（写 `scripts.json`，§7.1）。
4. 跑**本脚本自己的**测试：`--validate` 过、`--selftest` 全绿、
   `python scripts/<名>/test/run.py` 全绿、内核名扫这一个脚本零命中（§6）。
   **只跑这一个脚本**，不跑别的脚本、不跑仓库级体检（AGENTS.md 第 12 条）。
5. **出货**：把改动的 `.ahk` 复制进宿主 `Scripts` 目录（**平铺**，只复制 `.ahk`，
   不复制 `info/`）。宿主扫的是平铺 `.ahk`，文件夹结构只是仓库里的组织形式。
   改名时先删宿主侧的旧名 `.ahk`，再放新名，避免新旧并存。
6. **实机门禁（硬规矩）**：经 AHKDeck MCP 在宿主里完成实机闭环——`list_scripts` → `run_script` →
   `get_session_output` → `stop_script`/`stop_all`。会话输出无内核报错、托盘入口/版本号/行为都对、
   常驻类脚本停止后不留副作用，才算过（见 §6）。结论记入 `info/HISTORY.md` 或 `.plan` 文档留痕。
7. **先提交源码（发版顺序第一步，不可颠倒）**：把该版本全部改动一并 commit 并 push 到 master
   ——脚本 `.ahk`、头部 `@version`/`@date`、`info/HISTORY.md`、清单 `scripts.json`、
   `history/<id>.json`、README；多文件脚本还要先跑 `python tools/pack_script.py <名>` 生成
   `dist/<名>.zip` 供上传作附件（**`dist/` 是打包产物、已 gitignore，不入库**——需要时重新
   生成即可，云端 release 附件才是权威）。清单与 history 的地址由 `<id>-<版本>` 推导、不依赖上传结果，
   可在 `-Apply` 前按最终内容写好（`-Apply` 重写这两份是幂等的，不产生新 diff）。
   **提交必须发生在打 tag 之前**——tag 要指向含这一版全部改动的 commit，否则按 tag 回滚拿到旧代码。
   默认不自动 push / 不代传：推送与发布由作者本人做。
8. **再打 tag、最后上传（纪律见 §7.2）**：在步骤 7 已提交的 HEAD 上调用
   `python tools/publish_version.py <名>` ——先 dry-run 核对，确认无误再 `-Apply`；
   工具先在已提交 HEAD 上建 tag `<id>-<版本>` 并 push，再建两端 release、上传附件，
   最后复核双端下载地址 200。**提交在前、tag 在后，tag 自然指向含该版本的 commit。**
   绝不能先 `-Apply` 建 tag 再回头提交源码。**tag 名 / 附件名 / 清单地址不要手改或手填**（§7.2）。

> **★ 发版顺序硬规矩（用户裁决，不可颠倒）：先提交源码 → 再打 tag → 最后上传附件。**
> commit/push 在前，tag 居中（指向含该版本的 commit），附件上传在最后。
> 绝不能"先建 tag 再提交源码 / 改清单"——那样 tag 指向发版前旧 commit。
> 2026-11-16 夜灯 1.2.4 / 打开方式清理 1.5.7 首版踩过此坑（tag 落在提交前），故立为硬规矩。

> 出货有两条互不冲突的路：日常开发把改动的 `.ahk` 复制进宿主 `Scripts` 平铺目录（步骤 5），
> 本地立刻能测；正式发版把附件传 release 并更新清单 / 历史（步骤 8），所有用户才下载得到。
> 两条都要做，不是二选一。宿主不做自动升级；版本历史链接由宿主信息窗给出，用户自己点开看。

### 7.1 机器清单 scripts.json 与版本历史 history/<id>.json

两份都是生成物，宿主联网读取：

- `scripts.json`：当前版本清单，回答「有哪些官方脚本、现在该下哪个地址」。
- `history/<id>.json`：单脚本版本历史清单，回答「这个脚本发过哪些版本、各版本附件在哪」。
  宿主在「脚本详情」窗里显示「版本历史（Gitee）/（GitHub）」两个可点击链接，指向这两条 URL。

**清单形状**：顶层对象 `{ "name": "AHKDeck", "scripts": [...] }`，一项一脚本，无 sha256。
宿主也兼容旧的顶层裸数组。每项字段 = 头部 12 必填的直接投影 + 计算字段：

| 字段 | 来源 |
|---|---|
| `name` `id` | 头部 `@name`（中文，= 文件夹名 = 文件名）、`@id`（永久英文身份，§5） |
| `version` `date` `description` `author` `license` `requires` `host` `entry` | 同名头部字段 |
| `path` | 相对仓路径 `scripts/<名>/<名>.ahk` |
| `size_kb` | **实际附件**字节数 ÷ 1024（1 位小数，仅供显示）。`.ahk` 折成 LF 大小（量 git 存储字节，不量 CRLF 工作副本）；zip 按原始字节 |
| `gitee` `github` | release 附件地址：`https://gitee.com/<owner>/<repo>/releases/download/<id>-<版本>/<附件名>`（GitHub 对应 owner 见下） |
| `package` `packageGithub` | zip 包附件地址，宿主靠它判定包模式；单文件脚本为空，zip 时与 `gitee`/`github` 同址（§9.3） |
| `history` | `https://raw.giteeusercontent.com/<owner>/<repo>/raw/master/history/<id>.json`（直连 CDN，理由见下） |
| `historyGithub` | `https://raw.githubusercontent.com/<gh-owner>/<repo>/master/history/<id>.json` |

**地址推导**：`<owner>/<repo>` 取自 `@namespace`；github 的 owner 由 gitee owner 换
（`qiuzongman`→`zongmanqiu`，只换主机名会 404）；tag = `<id>-<版本>`，纯 ASCII，中文不再进 tag。
附件形态的**唯一判据 = 脚本结构有没有附属文件**（`pack_script.has_attachments()`）：有附属文件才用 zip，
且每次从当前源码现打（`build()`）并校验包内入口 `@version` 与目标版本一致，不一致就拒绝发布/生成清单；
无附属文件用单 `.ahk`。**绝不看 `dist/` 里有没有残留旧包**——残留旧 zip 会让重发把上一版内容传上去
（2026-11-17 修复的隐患）。但**发布到两端的附件名一律是
ASCII `<id>.zip` / `<id>.ahk`**（中文名只进清单 `name` 字段，见下）。**清单与 history 必须指向同一附件**，
否则发布后重生成清单会把 zip 脚本的地址改回 `.ahk`，下载 404。

**两端附件名统一为 ASCII `<id>.ahk/.zip`（实测踩坑）**：GitHub 的 uploads 端点不接受 URL 编码的
中文 `name=`——实测会静默存成 `default.ahk`，清单里的中文 URL 全部 404。故**两端都用同一个 ASCII 名**
`<id>.ahk/.zip`：Gitee 上传时用 curl 的 `filename=` 覆盖本地中文名，GitHub 建 release 后单独走
uploads 端点显式传 `name=`。中文显示名由清单 `name` 字段提供，**不进附件文件名**——两端下载链接的
文件名必须完全相同，否则不可接受。若需重建已存在的 release（改附件名），Gitee 用
`DELETE /releases/{id}` 后重发，GitHub 附件已是 ASCII 则不必动。
`history` / `historyGithub` 钉默认分支 `master`（每次发版都被覆盖成最新），不钉 tag。
**Gitee 侧必须用 `raw.giteeusercontent.com` 直连域名**：`gitee.com/<owner>/<repo>/raw/...` 会 302 到
`raw.giteeusercontent.com/...?signature=...` 这种带**时效签名**的地址，签名过期或转存后即失效，
外站 Referer 还会被防盗链拦成 403。直连形式无签名、无跳转，实测 7 个脚本的历史清单全部 200。
所有 URL 只接受 HTTPS；宿主解析时非 HTTPS 的历史链接会被清空，但该脚本行仍有效。

**生成器** `tools/make_index.py`（Python3，无第三方依赖）：扫 `scripts/<名>/<名>.ahk` → 解析头部 →
校验 12 必填（含 `@id` 形状与全仓唯一）→ 算 path / size_kb / 附件地址 / 双源历史链接 →
按 name 排序写 `scripts.json`（indent=2、ensure_ascii=False、尾换行，确定性输出）。

- `python tools/make_index.py`：写清单（**唯一的动作**）。
  `--check` / `--audit` / `--selftest` 三个分支 2026-11-14 已删：它们是「全仓一次性扫」，
  改一个脚本时会把其余脚本的旧账一起变成红灯（AGENTS.md 第 12 条）。
  生成器自身的正确性靠 `scripts.json` 的 git diff 看 —— 只该多出/改动你动过的那一项。
- **发布时不要单独手跑生成器**：`publish_version.py` 会先更新 `history/<id>.json` 再自动调用它；
  顺序反了会让两份清单指向不同附件。

**手改生成物无意义**：`scripts.json` 与 `history/<id>.json` 下次运行工具就被覆盖；
要改信息去改脚本头部 / release 发布流程。

### 7.2 发版：每脚本每版本一个 release

版本权威在远端 release，不在本地。每个脚本的每个版本各建一个独立 release，
tag = `<id>-<版本>`（如 `night-light-1.2.3`），纯 ASCII，杜绝中文 tag 与日期 tag 的歧义。

**前置硬条件（先提交 → 再 tag → 再上传，见 §7 步骤 7/8）**：调用 `-Apply` 之前，该版本的全部源码改动
（脚本、头部版本、HISTORY、清单、history json）必须已 commit 并 push 到 master。工具**不会替你提交**，
它只在当前 HEAD 上建 tag——所以提交在前，tag 才指向该版本；反过来先在旧 HEAD 建 tag 就固定了错误指向。

工具 `tools/publish_version.py <脚本名>`（默认 dry-run）：

1. 读脚本头部 `@id` / `@version`，从 `info/HISTORY.md` 取该版本小节作发布说明并脱敏；
2. 附件形态由 `has_attachments()` 判：脚本有附属文件就 `build()` 现打 zip 并校验包内 `@version`，
   无附属文件用单 `.ahk`（不看 `dist/` 残留，§7.1）；zip 时生成器同时填 `package` / `packageGithub`；
3. 建 tag `<id>-<版本>` 并推送 → Gitee release + `attach_files` 上传附件 →
   GitHub `gh release create` 传同一附件（源码只 push Gitee，GitHub 靠仓库镜像同步；附件两端都传，见下）；
4. 写 `history/<id>.json`（追加/替换该版本一条，含两端地址与大小）→ 重生成 `scripts.json`。

```bash
python tools/publish_version.py 夜灯              # dry-run：只打印将做什么
python tools/publish_version.py 夜灯 -Apply        # 两端都发
python tools/publish_version.py 夜灯 -Apply -Only gitee
```

**安全纪律**：默认 dry-run，显式 `-Apply` 才真发；凭据走 git credential manager / `gh` keyring，
token 不进代码、不进日志、不进 argv；Gitee API 正文非 ASCII 转 `\uXXXX`（避免 Latin-1 解码问题）。
**同版本重发**（改了发布说明或附件要重传同一版本，例如附件里只有文件头注释落后）：
Gitee 侧先查后建——release 已存在就 `PATCH` 更新正文与标题（照 `.main/build/7_release.ps1`），
不再因 tag 已存在而崩在半途；GitHub 侧 release 已存在就跳过 `create`，同名资产先删后传。
两端都不需要人先去平台上删 release，但**附件仍是新建**，重复跑会在 Gitee 留下同名多份，重发前先确认。

**源码单源 / 附件双源（用户裁决，2026-11-17）**：
- **源码只 push Gitee**：`commit` / `tag` / `push` 一律只推 Gitee（`git push origin master`、`git push origin <tag>`）。
  GitHub 仓库开了镜像同步，Gitee 推完 GitHub master 与 tag 自动跟到同一 commit——**不要手动 push GitHub**
  （手动推会报 `cannot lock ref`，因为远端已被镜像更新到同一值）。origin 只有一个，就是 Gitee。
- **附件两端都传**：release 附件必须 Gitee（`attach_files`）+ GitHub（uploads 端点）各传一份，文件名相同；
  tag / release / 附件 / 历史链接必须成对存在。任一端失败就停下修，不要留「一端有一端无」的清单。

## 8. 新增一个脚本（标准流程）

9 步闭环，每步过不了**就停在那一步修**，不往下走：

| 步 | 做什么 | 命令 / 动作 | 过的标准 | 不过怎么办 |
|---|---|---|---|---|
| 1 | **定形态、选范本** | 读一份形态最像的范本源码（见第 2 步） | 能说出自己的窗口属于哪一类 | — |
| 2 | **建骨架**：先跑 `python tools/new_script.py <名> "<一句话功能>" <英文id>`（m213/m221）——自动生成 §10 八色窗体、`info/`、`test/run.py` 骨架，头部带 `@id`；纯托盘/无 GUI 等特殊形态照抄对应范本，删掉模板里用不到的控件 | 能说出自己的窗口属于哪一类 | 生成器拒绝重名/非法名/重复 id；形态不符就换范本 |
| 3 | **语法** | `.build/AHKDeck.exe --validate "<路径>\<名>.ahk"` | `{"ok":true,"rc":0}` | 看 `errors[].line` + `source` 修；宿主报错带内核原话 |
| 4 | **静态门禁** | `python tools/ui_static.py <名>`；有码表再加 `python tools/check_codes.py <名>` | `总计失败 0 项` | 按 FAIL 项改：S 系列是版本四处一致 / 调色板 / 出货件一致；C 系列是码表与权威表比对 |
| 5 | **自测** | `<名>.ahk --selftest` | `rc=0` 全绿 | **拿修复前的代码跑一次确认会红**——只会绿的断言不是断言 |
| 6 | **实机闭环（硬规矩）** | MCP：`list_scripts` → `run_script` → `get_session_output` → `stop_script`；有界面加 `wait_ui`（异步就绪）、`inspect_ui`（几何）、`send_input`（交互）+ `capture_ui(stable=2)` → `ui_diff`（像素回归）→ `assert_ui`（判定） | 会话输出无内核报错、托盘入口/版本/行为都对、几何逐项吻合、diff 有据、assert verdict=pass、停止后无残留 | 报错先看 `source` 与 `stack`（§6）；量测与判定口径见 docs\MCP界面量测.md |
| 7 | **登记** | `info/README.md` 写功能/入口/**写入位置逐个列出**/风险/不做；`info/HISTORY.md` 首段 `## 1.0.0（日期）`；根 `README.md` 脚本表加一行；`python tools/make_index.py` | `scripts.json` 的 diff **只多出自己这一项** | 写入位置必须都符合 §1「产物进同名文件夹」 |
| 8 | **出货** | 复制 `.ahk`（只 `.ahk`，不带 `info/`）进宿主 `Scripts` 平铺目录；`cmp` 对比 | 逐字节一致 | 改名时先删宿主侧旧名再放新名 |
| 9 | **发版** | 提交并 push；多文件脚本先 `pack_script.py <名>`；`publish_version.py <名>` 先 dry-run 再 `-Apply`（§7.2） | tag `<id>-<版本>` 两端一致；历史链接可点开；清单与 history 指向同一附件 | 任一端失败先修，不留半套 |

**只有 `--selftest` 分支还不算有测试**（第 5 步只证算法，不证窗口真的画出来了）：
新脚本进仓时可以没有 `test/`，但**下次改到它**就得补上（`run.py` + 靶窗 `.ahk` + `README.md`），
靶窗要能复现该脚本最怕的那类缺陷。

**改既有脚本**走同一张表：跳过第 1–2 步（形态不变时），第 7 步按 §5 升版本 + 写 HISTORY。

若复刻/移植了别的项目，在该脚本头部注释与 `info/README.md` 写明来源与许可（§9）。

## 9. 多文件脚本包（zip 发行）

单 `.ahk` 装不下的脚本（要带 DLL、数据表、自研取数工具），走包模式。宿主 0.3.6 起支持
下载 zip → 校验 → 解压安装；包格式与打包工具都是定死的，别发明新形状。

### 9.1 包契约（宿主逐项校验）

- zip 根 = **`<名>/`**，入口 = **`<名>/<名>.ahk`**；`@name` = 目录名 = zip 名，三者一致。
- **附属文件放 `scripts/<名>/` 根**（与 `<名>.ahk` 同级）。安装后入口落 `Scripts\<名>.ahk`，
  其余文件落 `Scripts\<名>\` —— 与单文件脚本同一种"平铺"形态，脚本用 `A_ScriptDir\附属文件`
  直接读，产物也写进同一个同名文件夹。
- 宿主 0.5.0 起**只把 `Scripts\` 根下的 `.ahk` 当脚本**，不再搜索任何子目录：因此
  `Scripts\<名>\` 永远只是这个脚本的数据目录，不会被当成脚本，也不会和"分组"混淆。
- info/、test/ 与内层 `<名>/`（运行时产物区）**不进包**——打包工具自动排除。

### 9.2 打包

```bash
python tools/pack_script.py <脚本名>          # 输出 dist/<名>.zip
python tools/pack_script.py <脚本名> --list   # 先看会打进什么
```

压缩器优先 7-Zip（`7z a -tzip -mx=9`，包更小），找不到则退回 Python zipfile——
**两者产物都是标准 zip（Deflate）**：宿主预校验后用系统自带能力解压
（资源管理器同一套代码），也能直接双击打开。
产物经包契约自检（root/@name/禁带 info、test）。

### 9.3 登记与安装侧

- m221 起单文件与 zip 包共用 `gitee` / `github` 作为 release 附件地址；生成器按脚本结构
  判定（`has_attachments()`）：有附属文件就是 zip，`build()` 现打并校验包内 `@version`，
  把同一地址也写进 `package` / `packageGithub`；无附属文件是单 `.ahk`，这两个字段为空。
  宿主 DownloadDialog 见 `package` 非空即按包安装（下载 zip → 预校验 → 系统解压 → 校验入口头 →
  入口平铺落盘、其余进同名目录、旧的两者都备份进 `temp\deleted`）。
- `history/<id>.json` 记录同一附件地址（§7.1），与清单的 `gitee` / `github` 必须一致，
  否则点开「版本历史」下到的是另一个文件。
- 版本判定读 `Scripts\<名>.ahk` 的头部，与单文件同一套。
- 打包脚本「编译为 EXE」暂不跟随附属目录——需要 exe 的包脚本先别做（写在 README 不做清单）。
