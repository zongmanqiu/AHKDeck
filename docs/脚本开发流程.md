# AHKDeck 官方脚本开发流程

> **定位**：回答「一个脚本/一次修改，从头到尾按什么顺序做、每步用什么工具、
> 期望看到什么结果、不过怎么办」。设计标准见 [`UI规范.md`](UI规范.md)，组件用法见 [`UI组件手册.md`](UI组件手册.md)，
> 踩坑证据与取证方法学在 [`UI踩坑.md`](UI踩坑.md)；仓库规约（目录/头部/版本/发版）
> [`开发指南.md`](开发指南.md)（本目录同步副本，真源在脚本开发仓库）——四份各管一段，本文管**过程**。
>
> 本文所有命令都经过实机验证；「预期结果」列写的是**可判定的输出**，不是感觉。

---

## 0. 总循环（一张图）

```
定范围 → 定形态读范本 → 写代码 → 静态门禁 → 语法门禁 → 自测
   ↑                                                    ↓
   └──── 修复 ←── 取证定位 ←── 失败? ←── 实机闭环(MCP/测试脚本) ←┘
                                    ↓ 通过
                              登记 + 发版 + 同步出货件
```

两条铁律贯穿全程：

- **改哪个脚本只测哪个**。不顺带跑别的脚本、不顺手改别的文件（发现别的问题记下来，
  另开任务）。这是仓库 AGENTS.md 第 12 条。
- **新断言先能红，再信它的绿**。任何新写的检查/断言，拿「修复前」的代码跑一次确认它真的报错——
  只会绿的断言比没有更坏（它会给你假通过，`UI踩坑.md`「取证方法学」与 K40 的实案）。

---

## 1. 第一步：定范围与形态（动手前 10 分钟）

**做什么**：

1. 写下一句话范围：改哪个脚本、改什么、不改什么。
2. 判断窗口形态，**读一份最像的范本源码**（不是通读文档，是读代码）：

| 形态 | 读谁 | 重点 |
|---|---|---|
| 单页表单（字段行/勾选/日期） | `scripts/文件时间修改/` | 控件配方区、`FlatCheck`、`ClipField` |
| 单页大列表（拖入/扫描/状态条） | `scripts/文件哈希/` | 列表区外框、状态条、双击复制 |
| 多页导航 / 长滚动列表 / 自绘列头 | `scripts/硬件信息/` | `BuildNav`、`class FlatScroll`、`Layout()`、右键菜单、`OnSize` |
| 纯托盘无 GUI | `scripts/防休眠/` | 文案一致性即可 |

3. 用到的组件先查 [`UI组件手册.md`](UI组件手册.md) §10 速查表——**坑都有编号，先看再写**。

**为什么**：硬件信息 2.0.0→2.3.2 返工十几次，没有一次是配色问题，全是「这类结构第一次做」。
读源码能直接跳过 K42–K48 那一批坑。

**产出**：一句话范围 + 选定的范本 + 要用的组件清单。

---

## 2. 第二步：写代码

**规矩**（细则见 [`开发指南.md`](开发指南.md) §4）：

- 照抄范本的骨架、令牌、配方，**不自造色值/字号/新画法**（`ui_static` 会拦第九个颜色）。
- 新类声明放在 auto-execute 调用之前（K18，否则 `/validate` 被模态框卡死）。
- 运行期产物路径一律 `A_ScriptDir\<脚本名>\...`（含配置、备份、报告、自测输出）。
- `@version` / `@date` 改完当场升，别攒到发版时。

---

## 3. 第三步：静态门禁（秒级，先跑最便宜的）

```bash
# 脚本仓库根目录下
python tools/ui_static.py <脚本名>        # 调色板/字号/版本四处一致/出货件一致，共十项
python tools/check_codes.py <脚本名>      # 有码表（枚举 Map）的脚本必跑；--from-dmidecode 可反查权威表
```

**预期结果**：`总计失败 0 项` / `全部通过`。

**不过怎么办**：按 FAIL 项的文案改。S 系列报色值/字号 → 回 `UI规范.md` §10.2 查令牌；
版本不一致 → 同步 `@version`/`HISTORY`/`README`/`scripts.json`/`.build` 五处。
改完**立刻重跑**，不要攒。

---

## 4. 第四步：语法门禁

```bash
# 方式一：独立解释器（快，适合快速迭代）
.build/AutoHotkey64.exe "<脚本路径>" --selftest   # 构建必得，门控变量不设时就是原版 2.0.31
# 方式二：宿主（与发行环境同内核）
.build/AHKDeck.exe --validate "<脚本路径>"
```

**预期结果**：`--validate` 退出码 `0`；语法错是 `2` 且带 `line` 与内核原话。

**不过怎么办**：按行号修。注意两类高频误因：
- 类/函数定义在 `return` 之后（K18）；
- 变量名撞了 AHK_H 专有内建（如 `sizeOf`），宿主内核隔离门禁会拦——换名。

---

## 5. 第五步：功能自测（`--selftest`）

**做什么**：给脚本写无 GUI 的自测分支（`--selftest [输出路径]`），断言纯函数与码表。
输出默认写 `A_ScriptDir\<脚本名>\selftest-result.txt`。

**预期结果**：每个断言 `PASS`，末尾 `fails=0`。

**不过怎么办**：先怀疑断言本身——它是不是按错误理解写的？（硬件信息 2.3.0 的教训：
`TypeName(32)="DDR5"` 这种按错表写的断言把 bug 固化成 PASS。修法：断言跟着权威源码走，
并补反向用例——喂一个会暴露差异的输入。）

---

## 6. 第六步：实机闭环（GUI 脚本必做）

这是最贵也最能抓真问题的一步。工具链三层，按成本从低到高排：

### 6.1 MCP 闭环（首选）

宿主端点：`.build/AHKDeck.exe --mcp-stdio`（0.3.6 起 18 工具，2026-11-16 加判定工具后 20 工具）。
脚本平铺进 `.build/Scripts` 才会被 `list_scripts` 看见。

固定闭环（看）+ 交互闭环（动）+ 像素回归（比）+ 判定（断）：

```
edit_editor → validate_editor → run_editor → get_session_output
→ wait_ui（异步就绪先等）                       # 等：窗口/列表还没建好时
→ inspect_ui(items=true) → capture_ui          # 看：几何与内容
→ send_input（click/wheel/key/text）           # 动：验证回调/滚轮/菜单（K32/K45/K46）
→ capture_ui(stable=2) → ui_diff               # 比：像素回归断言
→ assert_ui                                    # 断：工具直接给 pass/fail
```

- `inspect_ui`：返回顶层窗口与全部子控件的类名/文字/`client` 矩形/可见性。
  **几何断言逐项比 `client`**，口径与 `UI规范.md` §10.3 坐标表一致（字段语义见
  `docs/MCP界面量测.md`）。
- `capture_ui`：抓窗截图，供像素复核；交互/滚动之后加 `stable=2` 防「截到重绘中间态」。
- `send_input`：注入点击/滚轮/键盘——回调用错（K32）、右键菜单挂错（K45/K46）这类
  截图验不出的 bug，现在能在闭环里自动验证。
- `ui_diff`：两张截图逐像素比对，返回差异像素数、包围盒、行段（bands）——
  排序位移、裁字残影这类像素回归从手写探针变成一行断言。
- `assert_ui` / `wait_ui`：按 `checks` 对界面树/条目求值，工具直接回 `verdict=pass/fail`，
  不用再肉眼比对 `inspect_ui` 输出；异步窗口或列表先用 `wait_ui` 等就绪再断言。
  参数与字段路径见 `docs/MCP界面量测.md`。
- 脚本级测试固化成 `scripts/<名>/test/run.py`（`from mcp_client import MCP`），
  下次改这个脚本直接复跑当回归。

### 6.2 真机截图取证（手工/探针）

实测过的三种抓法与适用范围：

| 方法 | 能拿到什么 | 限制 |
|---|---|---|
| MCP `capture_ui` / `PrintWindow` | 窗口自身内容，不抢前台 | 与真实屏幕渲染路径不同，**验不了重绘残留类问题** |
| 屏幕抓图（BitBlt）+ 置顶 | 真实渲染 | ① 必须 Per-Monitor DPI Aware 后按物理像素换算坐标（否则抓到别的窗口）；② **自己 Popen 的脚本跑在隔离桌面**，置顶压不上、屏幕抓图抓到的是用户前台——**别去抢用户的前台**，破坏性 UI 动作交用户手测 |
| 用户实机复现 | 最终裁决 | 用户给截图后，逐行量像素，别靠目测 |

**像素判读硬规矩**（血泪教训，详见 `UI踩坑.md`「取证方法学」）：

1. **只看终态 = 白验**：填表/扫描类缺陷在中间态。抓 0.8/1.2/1.6/2.0s 各一张。
2. **数值化读图，不靠目测**：按行块（如 23px 网格）量每行文字墨迹范围
   （正常 `6..17px`），对齐网格、量墨迹高度——「看起来被裁」可能是放大裁图的伪影，
   像素数据不会骗人。
3. **先定阶段再看像素**：状态栏文字是阶段指纹。
4. **采样带用 `GetWindowRect`**（含非客户区）；`GetClientRect` 不含滚动条，会整整错开 16px（K40）。
5. 数值离谱（满宽像素骤降、一整片陌生色）先怀疑**窗口被遮挡**，别急着改代码。
6. `WM_MOUSEWHEEL` 发给焦点窗口：测滚轮先点一下列表激活，不动重试一次，否则有 0→0 假失败。

### 6.3 对照实验（定位根因的杀手锏）

改不准根因时，做**单变量对照**：复制当前脚本成 `.temp/变体A.ahk`，只改一处
（如去掉某个 `OnMessage`、改一个返回值），同一探针跑两个版本比像素数据。
打开方式清理 1.5.6 的裁字问题就是靠「关 custom draw / 改返回值」两个变体定位到
`CDRF_NEWFONT` 误用的；最终验收也是「修复版 vs 还原旧逻辑版」滚 30 轮对比墨迹带。

**产出**：像素级证据（改前/改后的墨迹范围、网格对齐、差异像素数）。

## 7. 失败了怎么办：修复循环

```
复现（探针/最小路径） → 二分隔离（变体对照） → 修根因（不修表象）
→ 重跑本步门禁 + 像素对比 → 写回归断言 → 记 K 表
```

- **复现优先于修复**：不能稳定复现就不要改代码——改了也验证不了。
- **二分隔离**：现象涉及多个机制（如「滚动+自绘+双缓冲」）时，逐个关掉做变体，
  锁定唯一变量再修。
- **修完必验三层**：① 原探针再跑（问题消失）；② 对照副本再跑（探针能抓到旧 bug，
  即断言「能红」）；③ 该脚本 `test/run.py` 复跑（无回归）。
- **每次修复都问一句**：这个坑该不该进 `UI踩坑.md` 的 K 表？该进就写
  （现象 + 正解 + 实测证据），下个脚本才不会重犯。K1–K50 就是这么攒出来的。

**反复测试的原则**：不是无脑重复跑，而是**每轮只改一个变量**，改完立刻全量重跑
该脚本的门禁链（静态→语法→自测→实机），确认没有引入新回归再进入下一轮。

## 8. 第七步：登记与发版（全部通过后才做）

按 [`开发指南.md`](开发指南.md) §5/§7 执行，要点：

1. `@version`/`@date`、`info/HISTORY.md` 新段落（写**修了什么 + 怎么验的**，含数据）。
2. `info/README.md` 的写入位置与风险段与实际行为一致。
3. 根 `README.md` 脚本表行更新。
4. `python tools/make_index.py` 重生成 `scripts.json`（m221 起清单直接指向 release 附件，不再有 `TAG`
   常量、也不需要额外打清单 tag）。发版走 `python tools/publish_version.py <名>` 先 dry-run 再 `-Apply`：
   **先提交源码 → 再打 tag `<id>-<版本>` → 最后传附件**，顺序颠倒会让 tag 指向发版前的旧 commit。
5. `.build/Scripts/<名>.ahk` 覆盖同步并 `cmp` 校验；宿主侧 `.build/docs/scripts.json` 同步。
6. 做一次 `.bf` 快照。

**git commit / tag / push 只在用户点头后做。**
